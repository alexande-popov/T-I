# Инвестиционное приложение на Python с T-Bank Invest API

## 1. Цель и принципы

Продукт — персональный инвестиционный ассистент для частного инвестора, который ведёт портфель на T-Bank Инвестиции.

Главный принцип: **каждая функция должна либо экономить время, либо улучшать решения, либо снижать риск**. Всё остальное — потом.

Продуктовая рамка:

> Приложение автоматически собирает историю сделок, показывает динамику портфеля и структуру активов, помогает планировать налоги и исполняет торговые стратегии по заданным правилам.

## 2. Функциональность по этапам

### 2.1. MVP: «пульт портфеля»

- Подключение к T-Bank Invest API.
- Хранение токена в `.env` / keyring. На старте — read-only токен.
- Получение списка счетов.
- Текущие позиции: тикер, количество, средняя цена, текущая цена, стоимость, P&L.
- Свободные деньги и общая стоимость портфеля.
- История операций и сделок.
- Котировки, свечи, стакан по нужным тикерам.
- Расчёт:
  - доля каждой бумаги;
  - прибыль/убыток по позиции;
  - комиссии;
  - доходность за день/неделю/месяц/всё время.
- График стоимости портфеля.
- Экспорт в CSV/Excel.
- Уведомления в Telegram:
  - цена ниже/выше заданной;
  - изменение за день больше X%;
  - отчёт раз в день/неделю.

### 2.2. Аналитика

- Реальная доходность с учётом пополнений и выводов: XIRR / TWR.
- Распределение по секторам, валютам, эмитентам.
- Волатильность, максимальная просадка, Sharpe.
- Сравнение с бенчмарком: IMOEX / RTS.
- Дивидендный календарь и прогноз дивидендов.
- Ребалансировка: целевые доли, расчёт покупок/продаж.
- Простой бэктест стратегий.

### 2.3. Торговля

- Sandbox-режим T-Bank Invest API.
- Ручные заявки: лимитные, рыночные.
- Стоп-лосс / тейк-профит, если поддерживается API.
- Автостратегии:
  - ребалансировка;
  - усреднение;
  - следование сигналам.
- Обязательно:
  - журнал действий;
  - защита от дублей заявок;
  - лимиты на сумму сделки;
  - «kill switch» — кнопка «остановить всё».

### 2.4. Учёт и налоги

- Импорт сделок.
- Расчёт FIFO.
- Отчёт по прибыли/убыткам.
- Сверка с брокерским отчётом.
- Оценка налогов.
- Экспорт для налоговой.

### 2.5. Что не делать в первой версии

- Сложный веб-интерфейс.
- Мобильное приложение.
- Многопользовательскую систему.
- HFT и попытки «обогнать рынок».
- Автоторговлю без sandbox и логов.

## 3. Аналитика портфеля

### 3.1. Главная задача

Нужно показывать:

- как менялась стоимость портфеля во времени;
- сколько он стоит сейчас;
- сколько стоил неделю/год назад;
- соотношение по активам и как доли менялись со временем.

API брокера не даёт готовый график «сколько стоил портфель год назад». Его нужно реконструировать.

### 3.2. Два способа восстановления истории

**Способ 1: Реконструкция по операциям (backfill)**

1. Выгрузить всю историю операций по всем счетам (`OperationsService`).
2. Для каждой даты восстановить позиции: сколько каких бумаг было.
3. Умножить позиции на исторические цены закрытия.
4. Получить стоимость портфеля на каждый день.

Плюс: точная история с самого начала.
Минус: тяжёлая разовая операция, нужно учесть сплиты, амортизации облигаций, погашения.

**Способ 2: Снимки (snapshots)**

- Раз в день приложение сохраняет состояние: дата, счёт, тикер, количество, цена, стоимость, доли.
- Через год есть своя история, не зависящая от API.

Плюс: быстро, просто.
Минус: история копится только вперёд.

**Правильный подход:** сделать оба. Сначала backfill за прошлое, потом ежедневные снимки.

### 3.3. Схема БД для аналитики

```sql
snapshots(date, account_id, ticker, instrument_type, quantity, price, value, currency)
operations(operation_id, date, account_id, ticker, type, quantity, price, amount, currency)
prices(ticker, date, close, currency)
accounts(account_id, name, currency)
```

Примеры SQL-запросов:

- стоимость портфеля на дату;
- динамика за неделю/месяц/год;
- доля актива на дату;
- изменение долей между двумя датами.

### 3.4. Что показывать в интерфейсе

**Динамика стоимости**

- График общей стоимости по всем счетам.
- Переключатель периодов: 1д, 1н, 1м, 3м, 1г, всё.
- Отдельная линия — «вложено денег» (net cash flow). Тогда видно не «сколько стоит», а сколько ты заработал.

**Динамика структуры**

- Stacked area chart: как менялись доли активов во времени.
- Классификация по типу, сектору, эмитенту, валюте.
- Снимок на дату: таблица «тикер — доля — стоимость».

**Изменения между датами**

- «Что изменилось с прошлой недели»: топ-роста, топ-падения, изменение долей.
- «Что изменилось с начала года».

**Метрики**

- Прибыль/убыток за период в абсолюте и %.
- Изменение относительно вложенного.
- Вклад каждой позиции в общий результат.

### 3.5. Подводные камни

1. **Пополнения искажают график.** Нужна линия «вложено» и доходность, очищенная от пополнений (TWR/XIRR).
2. **Мультивалюта.** Приводить всё к рублю по курсу на дату или считать раздельно.
3. **Сплиты и корпоративные действия.** Тянуть дивиденды и сплиты через `InstrumentsService` и корректировать.
4. **Облигации.** Учитывать НКД, амортизацию номинала, погашение. Цена в API — в % от номинала.
5. **Rate limits.** Кэшировать котировки, не дёргать API без нужды.

## 4. История операций и база данных

### 4.1. Получение истории

В T-Bank Invest API использовать метод **`getOperationsByCursor`** сервиса `OperationsService`.

Важные нюансы:

- ID операций могут меняться. Не использовать `id` как первичный ключ. При повторной выгрузке лучше удалять старые записи и вставлять заново.
- Корпоративные действия могут делать историю неполной. Сверяться с брокерским отчётом.
- API имеет лимиты. Историю выгрузить один раз, потом докачивать новые операции.

### 4.2. Схема таблицы операций

```sql
CREATE TABLE operations (
    operation_id TEXT PRIMARY KEY,
    account_id TEXT NOT NULL,
    operation_date DATETIME NOT NULL,
    operation_type TEXT NOT NULL,       -- 'BUY', 'SELL', 'DIVIDEND', 'COUPON', 'FEE', 'INPUT', 'OUTPUT'
    ticker TEXT,
    instrument_type TEXT,               -- 'STOCK', 'BOND', 'ETF'
    quantity INTEGER,                   -- в лотах или штуках
    price REAL,
    amount REAL NOT NULL,
    currency TEXT NOT NULL,
    commission REAL DEFAULT 0,
    payment INTEGER DEFAULT 0,
    description TEXT
);

CREATE INDEX idx_operations_account_date ON operations (account_id, operation_date);
CREATE INDEX idx_operations_ticker ON operations (ticker);
```

`quantity` в API часто приходит в лотах. Нужно конвертировать в штуки через размер лота.

## 5. Налоги: FIFO и ЛДВ

### 5.1. FIFO

**FIFO (First In, First Out)** — при продаже бумаги списываются в порядке покупки, начиная с самых ранних. В России брокеры обязаны использовать этот метод для расчёта НДФЛ.

Пример:

1. Купил 10 акций по 100 руб.
2. Позже купил 5 акций по 150 руб.
3. Продал 5 акций по 125 руб.
4. По FIFO списываются 5 самых первых акций по 100 руб. Прибыль = 5 × (125 − 100) = 125 руб.

Чтобы считать FIFO самостоятельно, нужно реализовать FIFO-очередь для каждой бумаги. При продаже «достаются» самые старые лоты и считается разница.

### 5.2. Льгота долгосрочного владения (ЛДВ)

Позволяет не платить НДФЛ с прибыли, если бумага была в собственности **более 3 лет**. За каждый полный год владения сверх 3 лет даётся вычет 3 млн руб. За 3 года — 9 млн руб., за 4 года — 12 млн руб. и т.д.

Условия:

- налоговый резидент РФ;
- бумага обращается на организованном рынке;
- куплена после 1 января 2014 года;
- с 2025 года льгота распространяется только на бумаги компаний из ЕАЭС, обращающиеся на российских биржах. На иностранные бумаги (кроме купленных до 2022 года) ЛДВ не действует.

Приложение может для каждого лота рассчитать минимальную дату продажи, после которой сработает ЛДВ.

## 6. Торговля по стратегиям

### 6.1. Уровни автоматизации

1. **Генерация сигналов.** Приложение уведомляет о возможности сделки. Решение и исполнение — за человеком.
2. **Торговля по подтверждению.** Робот формирует сделку, ждёт подтверждения в Telegram.
3. **Полная автоматизация.** Робот сам принимает решения и исполняет сделки.

### 6.2. Источники сигналов

- Технические индикаторы: MA, RSI, MACD, полосы Боллинджера.
- Ребалансировка портфеля: следит за целевыми долями.
- Анализ волатильности: ATR и адаптивные стратегии.
- Анализ тональности новостей.

### 6.3. Архитектура торгового модуля

- `TinkoffClient` — обёртка API, соединение и отправка заявок.
- `SignalGenerator` — анализирует данные и выдаёт сигналы.
- `RiskManager` — проверяет сигналы на соответствие лимитам.
- `TradeExecutor` — выставляет заявки (`postOrder`).
- `TradeJournal` — лог всех действий робота.

### 6.4. Безопасность и риск-менеджмент

- Тестирование только в sandbox.
- Обязательные стоп-заявки: Stop Loss и Take Profit.
- Лимиты: максимальный размер позиции, сумма одной сделки, дневной убыток.
- «Kill switch» — мгновенная остановка робота и отмена заявок.
- Журнал всех действий.

## 7. Интерфейсы

### 7.1. Варианты

**CLI**

- Плюсы: пишется за вечер, легко автоматизировать, идеально для скриптов.
- Минусы: неудобно смотреть графики, неудобно с телефона.
- Для: backfill, разовые задачи, отладка.

**Telegram-бот**

- Плюсы: всегда в кармане, уведомления, команды, подтверждение сделок.
- Минусы: примитивные графики, неудобные таблицы.
- Для: ежедневный мониторинг, сигналы, алерты.

**Веб-дашборд (Streamlit)**

- Плюсы: графики, ползунки дат, таблицы, наглядно.
- Минусы: надо запускать, с телефона менее удобно.
- Для: аналитика, структура портфеля.

### 7.2. Рекомендация

Не «или», а «всё вместе», но по этапам:

| Задача | Интерфейс |
|---|---|
| Backfill, разовые скрипты, отладка | CLI |
| Ежедневные алерты, подтверждение сделок | Telegram-бот |
| Аналитика, графики, структура портфеля | Streamlit |

Порядок внедрения:

1. CLI сначала — ядро как библиотека.
2. Streamlit вторым — дашборд.
3. Telegram-бот третьим — уведомления и подтверждения.

### 7.3. Структура проекта

> **Примечание.** Ниже — вариант из исходного плана. Фактическая структура репозитория другая: код лежит в `src/` (`config.py`, `models/`, `services/`, `t_api/`), точка входа — `main.py`. При реализации приводить план к фактической структуре, а не наоборот.

## 8. Хранение и запуск

### 8.1. Где хранить данные

Для личного проекта лучший вариант — **SQLite**. Файл-база, не требует сервера.

Физически:

- локально на компьютере — для начала;
- на сервере (VPS) — для доступа 24/7;
- резервные копии обязательны: ежедневное копирование `.db` в отдельную папку или облако.

### 8.2. Где запускать

**Локально на компьютере**

- Плюсы: бесплатно, всё под контролем, легко отлаживать.
- Минусы: работает только когда компьютер включён.

**Raspberry Pi**

- Плюсы: работает 24/7, дёшево в долгосроке, данные дома.
- Минусы: нужно настроить самому, зависит от домашнего интернета.

**VPS**

- Плюсы: работает 24/7, доступ откуда угодно.
- Минусы: ежемесячная плата, нужно базово уметь работать с Linux.

**Streamlit Community Cloud / Render**

- Для веб-дашборда. Бесплатно, но бот там не запустить.
- Минус: бесплатные тарифы засыпают при простое.

### 8.3. Docker

Docker позволяет упаковать приложение со всеми зависимостями и запускать где угодно одной командой.

```bash
docker build -t invest-app .
docker run -p 8501:8501 invest-app
```

### 8.4. Безопасность токена

Токен T-Bank Invest API — ключ к деньгам. Не хранить в коде, не коммитить в Git.

Правильно:

- переменные окружения (`.env`, в `.gitignore`);
- системный keychain для продакшена;
- read-only токен на старте.

### 8.5. Рекомендуемый план

| Этап | Где хранить | Где запускать |
|---|---|---|
| Разработка | Локально, `data/` | Компьютер |
| Первые месяцы | Локально + бэкап | Компьютер |
| Доступ 24/7 | Raspberry Pi или VPS | Raspberry Pi / VPS |
| Дашборд | Та же БД | Streamlit Cloud |

## 9. Продуктовый процесс

### 9.1. Требования

**Видение** — зачем продукт существует. Один абзац.

**Функциональные требования** — по модулям:

- Портфель: сбор операций, текущие позиции, стоимость.
- Аналитика: динамика, структура, метрики.
- Налоги: FIFO, ЛДВ, налоговый календарь.
- Торговля: сигналы, заявки, риск-менеджмент.
- Интерфейсы: CLI, Telegram, Streamlit.

**Нефункциональные требования:**

- Безопасность: токен только в env, read-only по умолчанию.
- Надёжность: ежедневный бэкап БД, идемпотентность операций.
- Производительность: дашборд < 2 сек, backfill < 5 мин.
- Сопровождаемость: покрытие тестами ядра ≥ 70%, логирование.

### 9.2. Клиентские истории (user stories)

Формат: «Как <роль>, я хочу <действие>, чтобы <ценность>». Плюс критерии приёмки (AC).

**US-1. Просмотр динамики портфеля**

> Как инвестор, я хочу видеть график стоимости портфеля за период, чтобы понимать, как меняется капитал.

AC:

- переключатель периодов: 1н, 1м, 3м, 1г, всё;
- две линии: стоимость и вложенные средства;
- данные за выходные не проваливаются в ноль;
- график строится < 2 сек.

**US-2. Структура активов**

> Как инвестор, я хочу видеть доли активов по типам/секторам/валютам на дату, чтобы контролировать диверсификацию.

AC:

- выбор даты и группировки;
- stacked area chart по времени;
- сумма долей = 100%, включая кэш.

**US-3. Налоговое планирование ЛДВ**

> Как инвестор, я хочу видеть, какие лоты созрели для продажи без НДФЛ, чтобы оптимизировать налоги.

AC:

- для каждого лота хранится дата покупки;
- лоты ≥ 3 лет подсвечиваются;
- учёт правил ЛДВ после 2025 года.

**US-4. Сигнал о ребалансировке**

> Как инвестор, я хочу получать уведомление при отклонении доли актива от целевой, чтобы вовремя ребалансировать портфель.

AC:

- целевые доли в конфиге;
- порог отклонения настраивается;
- уведомление в Telegram.

**US-5. Тестирование стратегии в песочнице**

> Как инвестор, я хочу прогнать стратегию на sandbox-счёте, чтобы проверить её без риска.

AC:

- стратегия запускается только с sandbox-токеном;
- все сделки пишутся в журнал;
- kill switch останавливает робота < 5 сек.

### 9.3. Тесты

**Unit-тесты**

- FIFO-калькулятор на синтетических операциях.
- Расчёт долей: пустой портфель, одна бумага.
- Парсинг ответов API: моки клиента.
- Расчёт ЛДВ: 2 года 364 дня vs 3 года 1 день.
- Инструмент: `pytest`. Цель — 70% покрытия `core/`.

**Integration-тесты**

- Backfill на тестовой SQLite.
- Клиент API на sandbox.
- Кэш цен: повторный запрос не идёт в API.
- Инструменты: `pytest`, фикстуры, `vcrpy`.

**E2E-тесты**

- Запуск дашборда → график за год.
- Команда в бота → ответ.
- Робот в sandbox → сделка в журнале.

Не тестировать: UI Streamlit, форматирование графиков.

### 9.4. Развёртывание

**Среда разработки**

- Локально, `.venv`, SQLite в `data/`.
- Pre-commit: `black`, `ruff`, `mypy`, запрет коммита `.env`.
- Git: `main` — стабильная, `feature/*` — новые фичи.

**CI**

- GitHub Actions: на push — линтеры + `pytest`.
- Занимает 1–2 минуты.

**CD**

- Ручной триггер через тег `v1.0.0` → деплой на VPS.
- Docker-образ, `docker compose up -d`.
- Миграции БД отдельным шагом, бэкап перед деплоем.

**Мониторинг**

- Логи в файл + `logrotate` или `journalctl`.
- Telegram-алерт при падении.
- Ежедневная сводка: операции, ошибки, размер БД.

**Откат**

- Тэги в Git = версии.
- `git checkout v0.9.0 && docker compose up -d`.

**Квартал 4: Торговля**

### 9.6. Артефакты процесса

## 11. Ключевые технические решения

- Ядро отдельно от интерфейсов: CLI, бот и веб — разные «морды» над одной библиотекой.
- SQLite для хранения данных.
- `getOperationsByCursor` для истории операций.
- Ежедневные снимки + backfill для истории портфеля.
- FIFO-очередь для налогов.
- Sandbox для любых торговых стратегий.
- Telegram для алертов и подтверждений.
- Streamlit для аналитики.
- Docker для переносимости.
- GitHub Actions для CI.
- OKR для измерения пользы.
